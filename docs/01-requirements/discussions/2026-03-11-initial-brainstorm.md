## 核心需求讨论

### 1. 产品定位

**讨论内容**:
我们要做的不是简单的ChatGPT套壳，而是一个完整的AI Agent平台。核心差异化在于：

1. **Multi-Agent协作** - 支持多个专业Agent协同工作
2. **多LLM适配** - 灵活切换模型，利用免费额度降低成本
3. **个性化引擎** - 真正的长期记忆和人格塑造
4. **开放插件生态** - 用户可以自己写插件扩展功能
5. **多平台接入** - Web、移动端、浏览器插件、IDE插件、语音

**决策**:
✅ 定位为"AI Agent平台"而非"聊天机器人"
✅ 核心竞争力是Multi-Agent + 个性化 + 开放性

---

### 2. 核心功能模块

#### 2.1 LLM适配层

**需求描述**:
- 支持多个大模型提供商（Claude, DeepSeek, Kimi, 豆包等）
- 自动检测各模型的免费额度
- 智能切换：优先使用有免费额度的模型
- 支持手动指定模型
- 统一的接口抽象，上层业务无感知

**技术可行性**: ✅ 可行
- 各家API基本都遵循OpenAI格式
- 额度检测可以通过API或本地计数实现
- 需要处理不同模型的差异（如token限制、功能支持）

**优先级**: 🔴 P0 (MVP必须)

**潜在风险**:
- 不同模型的Function Calling格式可能有差异
- 额度检测的准确性
- 切换模型时的上下文一致性

**应对方案**:
- 建立完善的适配层测试
- 本地维护额度计数器
- 在切换时保留完整的对话历史

---

#### 2.2 Agent编排系统

**需求描述**:
- 支持定义多个专业Agent（日程、任务、检索等）
- Agent之间可以协作完成复杂任务
- 可视化的工作流编排界面
- 支持条件分支、并行执行
- 工作流可以保存、分享、复用

**技术可行性**: ⚠️ 有挑战
- Multi-Agent协调是技术难点
- 需要设计好任务分解和结果聚合机制
- 可视化编排可以参考n8n、Zapier

**优先级**: 🟡 P1 (v1.0)

**MVP简化方案**:
- MVP阶段只做单Agent
- v1.0再实现Multi-Agent和可视化编排

**技术选型讨论**:
- 考虑使用LangChain/LangGraph作为基础
- 或者自研更轻量的编排引擎

---

#### 2.3 个性化引擎

**需求描述**:
- 支持定义角色人设（性格、说话风格、背景）
- 长期记忆：记住用户的偏好、习惯、重要信息
- RAG支持：导入个人知识库
- 酒馆API集成：增强角色扮演能力
- 越用越懂用户

**技术可行性**: ✅ 可行
- 向量数据库技术成熟（Qdrant, Pinecone）
- RAG实现有成熟方案
- 酒馆API有现成接口

**优先级**: 🟡 P1 (v1.0)

**MVP简化方案**:
- MVP阶段只做基础的对话历史存储
- v1.0实现完整的个性化引擎和RAG

**成本考虑**:
- 向量数据库可以自建Qdrant（开源免费）
- Embedding可以用免费的模型

---

#### 2.4 插件系统

**需求描述**:
- 标准化的插件接口
- 插件沙箱隔离（安全性）
- 插件市场（发现、安装、管理）
- 支持用户自己开发插件
- 核心插件：日历、Todo、邮件、天气等

**技术可行性**: ✅ 可行
- 可以参考VS Code的插件机制
- 沙箱可以用VM2或Worker Threads
- 插件API设计需要仔细考虑

**优先级**: 🟡 P1 (v1.0)

**MVP简化方案**:
- MVP阶段内置几个核心功能，不做插件化
- v1.0实现完整的插件系统

---

#### 2.5 多平台接入

**需求描述**:
- Web应用（主要界面）
- 移动端App（iOS + Android）
- 浏览器插件（Chrome, Edge）
- IDE插件（VS Code, JetBrains）
- 语音对话（STT + TTS）

**技术可行性**: ✅ 可行
- 各平台技术都成熟
- 关键是后端API设计要统一

**优先级**:
- Web: 🔴 P0 (MVP)
- 浏览器插件: 🟡 P1 (v1.0)
- 移动端: 🟢 P2 (v2.0)
- IDE插件: 🟢 P2 (v2.0)
- 语音: 🟢 P2 (v2.0)

---

#### 2.6 数据采集

**需求描述**:
- 收集用户对话数据
- 收集用户行为数据
- 数据脱敏处理
- 导出为训练数据集
- 用于后续模型微调

**技术可行性**: ✅ 可行
- 数据收集很直接
- 需要注意隐私保护

**优先级**: 🟡 P1 (v1.0)

**隐私考虑**:
- 必须征得用户同意
- 提供数据脱敏选项
- 允许用户删除数据

## 技术架构讨论

### 后端技术栈

**讨论选项**:
1. Node.js + NestJS
2. Python + FastAPI
3. Go

**决策**: ✅ Node.js + NestJS

**理由**:
- TypeScript类型安全
- NestJS模块化好，适合大型项目
- 生态丰富，AI库也不少
- 团队熟悉度高
- 异步处理能力强

**保留意见**:
- Python在AI生态上更强，但考虑到团队技能和项目整体，选择Node.js
- 密集计算部分可以用Kotlin编译成WASM

---

### 数据库选型

**决策**:
- **关系数据库**: PostgreSQL（结构化数据）
- **缓存**: Redis（会话、队列）
- **向量数据库**: Qdrant（记忆、RAG）

**理由**:
- PostgreSQL功能强大，支持JSON
- Redis性能好，生态成熟
- Qdrant开源免费，性能好，易部署

---

### 前端技术栈

**决策**: ✅ React + Vite + TailwindCSS

**理由**:
- React生态最成熟
- Vite开发体验好
- TailwindCSS快速开发

**工作流编辑器**: React Flow

## MVP范围确定

### MVP核心功能（3个月）

**必须有**:
1. ✅ 基础对话能力
   - 接入2-3个LLM
   - 简单的上下文管理
   - 基础的意图识别

2. ✅ 日程管理
   - 日程CRUD
   - 时间冲突检测
   - 简单提醒

3. ✅ LLM适配层
   - 支持Claude + DeepSeek
   - 自动额度检测
   - 模型切换

4. ✅ Web界面
   - 聊天界面
   - 日程展示
   - 基础设置

**不包括**:
- ❌ Multi-Agent（v1.0）
- ❌ 个性化引擎（v1.0）
- ❌ 插件系统（v1.0）
- ❌ 移动端（v2.0）
- ❌ 语音（v2.0）

## 关键风险识别

### 技术风险

| 风险 | 影响 | 概率 | 应对 |
|------|------|------|------|
| Multi-Agent协调复杂度高 | 高 | 中 | 分阶段实现，MVP先不做 |
| 不同LLM的一致性问题 | 中 | 高 | 建立完善测试用例 |
| 插件安全性 | 高 | 中 | 沙箱隔离 + 权限控制 |
| 性能瓶颈 | 中 | 中 | 提前做压测 |

### 市场风险

| 风险 | 影响 | 概率 | 应对 |
|------|------|------|------|
| 大厂推出竞品 | 高 | 高 | 快速迭代，聚焦差异化 |
| 用户增长慢 | 中 | 中 | 加强运营推广 |
| 插件生态建设难 | 中 | 中 | 开发者激励计划 |

### 成本风险

| 风险 | 影响 | 概率 | 应对 |
|------|------|------|------|
| LLM API费用高 | 高 | 高 | 多模型切换，利用免费额度 |
| 服务器成本 | 中 | 中 | 优化架构，按需扩展 |
